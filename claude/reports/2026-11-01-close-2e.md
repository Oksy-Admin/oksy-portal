# Close 2e – Rule trial and check sets – 1-Nov-2026

## Built
- **Rule trial** (`rule_trials` table + `packages/worker/src/rule-trial-runner.ts`): "Run trial" on a hospital's page queues a job the worker picks up (same poll loop as the 2d "test before save" job, lowest priority — a diagnostic run, never the real daily work). It runs every ACTIVE check rule against the hospital's already-stored claims (`claims_staging`), reusing `selectRules`/`evaluateRules`/`contextFromStoredClaim` exactly as the real engine does, so a trial result can never disagree with what a real run would do. Writes a summary only (per rule: severity, claims hit, up to 5 `{tab, row}` examples; total claims, clean claims) — never a question, never a patient name or cell value.
- **Trial approval**: `approve_rule_trial(p_trial_id, p_note)` (Owner/Admin only — `has_role('ADMIN')`, which already passes Owner too), only once the trial has finished, recorded with who and when on the `rule_trials` row itself. Stage 4 (not built yet) will check this flag before sending a hospital's first questions.
- **Check sets** (`check_set_claims` table): Anoop picks up to 5 claims per hospital by searching claim number (Settled claims sorted first, since they no longer change); `pick_check_set_claim(p_record_uid)` snapshots the claim's key values (money, status, the dates that decide them — not operational text fields like courier number or remarks) and enforces the cap of 5, Owner/Admin only.
- **Live pass/fail, never cached**: the trial page computes pass/fail on every view by comparing the picked snapshot against the claim's *current* `claims_staging` values and current open Errors/Warnings from `issues` (`packages/rules/src/check-set.ts`, pure, no database). Pass = zero open Errors/Warnings and every key value still matches what was picked. A mismatch names the changed field(s) and/or the rule(s) now firing. This means the result can never go stale — no "last checked" cache to keep in sync with the worker's own runs.
- **Accept new values**: `accept_check_set_claim(p_id, p_reason)` — one click per failing claim, a reason is required (human decisions record a reason, decisions.md section 9), re-snapshots the claim's current values so the next check starts fresh. Owner/Admin only.
- **Page**: `/hospitals/[code]/trial`, linked from the hospital detail page. Run Trial button polls to a summary table; Approve button once finished; check-set table with Pass/Fail pills, per-claim "Accept new values" form, and a search-and-pick flow (hidden once 5 are picked).
- **Dev fixture + Playwright**: `/dev/trial` (fixture data, same pattern as `/dev/rules`) and `e2e/trial.e2e.ts` confirm Run Trial, Accept and the pick-search all refuse without a login.

## Choices made in the build
- **Check-set verification is computed live, not cached**: the stage-plan text suggested storing a "last check result," but reading `claims_staging` + `issues` fresh on every page view is simpler, cannot go stale, and needs no extra write path for the worker to keep in sync. The worker never touches `check_set_claims` at all.
- **"Key values" is a fixed field list** (`packages/rules/src/check-set.ts`'s `KEY_VALUE_FIELDS`), not the full `claims_staging` row: money, status, UTR, the dates and reasons that decide them — deliberately excludes operational text fields (courier number, remarks, follow-up log) so a claim is never flagged "changed" for something that was never part of its correctness.
- **Trial runs on stored claims, not a fresh sheet read** — "full data" in the plan text means the hospital's already-cleaned data, the same interpretation 2d's "test before save" job already used for a single draft rule. The existing "Run now" sheet-run levels (one sheet / one hospital / all) are untouched; trial is a separate, diagnostic-only job.
- **Question 5 ("check-set pass rule") resolved**: the stage-plan's own 2e bullet already spelled out the exact pass/fail rule in detail when the whole stage plan was approved 31-Oct; the "Questions for Anoop" tracker at the bottom of the section had simply not been updated to say so. Built exactly as that text describes (zero Errors/Warnings + unchanged key values; a legitimate change gets "accept new values"). Flagged to Anoop in the report below in case he wants it different.
