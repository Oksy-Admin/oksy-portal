## Built
- **Cross-row rules**, run after all rows of a hospital are read (`packages/worker/src/identity.ts`): same UTR on several claims (R-K01, new), same claim identity with different values (R-K02, split off from R-Y03's old double duty), same patient + same admission date (R-Y03, wording moved into the library). All three read severity/action/message from any ACTIVE CHECK rule with no `check_definition` in the Rule Library — no rule ID is named in `sheet-run.ts` or `clean.ts` (the no-hardcoded-rules test covers this); a rule made Inactive simply never fires.
- **Two-part approval** (`packages/rules/src/two-part.ts`): `findTwoPartCandidates()` detects the signature; `combineTwoPart()` re-cleans the primary row with the secondary's payments merged in — reusing `cleanRow` itself, not duplicating its money/engine logic, so Total Settled/TDS/Balance and every money rule are computed correctly over both parts. `markPending()` for an undecided candidate. Wired into `sheet-run.ts`: a new candidate is suggested once (`claim_links`, SUGGESTED); CONFIRMED combines and sets `combined_into_record_uid` on the secondary once both record_uids exist; REJECTED falls through to the normal conflict check (R-K02). Parts are never deleted or merged into one row.
- **"Value is correct"** (`packages/rules/src/confirmations.ts`, `issue_confirmations` table, `confirm_issue()`): fingerprint built from exactly the fields a rule reads (`engine.ts` `fieldsReadBy()`, generic — never the issueField alone, never a per-rule hardcoded list for an engine-driven rule). A Warning's issue row is marked CONFIRMED when the stored fingerprint still matches the live value each run; it reopens (OPEN) the moment the value changes. Errors cannot be confirmed (`confirm_issue()` rejects severity E). Owner/Admin only — no `clean_data` action tick exists yet; adding one is a small follow-up if Users should do this too.
- **Issue reason on the claims page**: `/claims` now shows each issue's rule ID and detail (title tooltip), and marks CONFIRMED ones; the query excludes a two-part secondary row (`combined_into_record_uid`) so a combined claim appears once.
- **Anoop's 3 new rules (1-Nov)**: R-K04 (policy number = phone number), R-K05 (Policy Holder Name empty with a claim number present), R-K06 (POD Number empty since the hospital's POD Start Date — with none set, the rule simply never fires: `pod_start_date` resolves to `null`, `AFTER` returns false, no extra code needed).

Existing values copied over by the migration.

## Choices made in the build
- A pending (undecided) two-part candidate is marked by suffixing the secondary's key early (`#2`) and flagging both rows `TWO_PART_PENDING`, with no issue raised — this reuses the exact mechanism the "different values" conflict case already had (a row keeps its own `claims_staging` row under a suffixed key), it just skips the R-K02 flag while a decision is pending.
- `combineTwoPart` re-invokes `cleanRow` for the primary row rather than hand-computing the combined totals, so there is exactly one place (already tested) that knows how Total Settled/TDS/Balance/money rules work; the secondary's own claim-level money issues (`settled_amount`, `balance_amount`, `tds_amount_stated`, `discount_amount`) are filtered out after the fact since "claim-level checks attach to the combined claim only" (decisions.md section 7) — a field-based filter, not a rule-ID list.
- `issues.status` gets a third value, `CONFIRMED`, rather than a separate table for "is this currently confirmed" — the row still exists for history; RESOLVED (the condition stopped firing) now also covers a row that was CONFIRMED, not only OPEN.
