# Close 2d – Rule Library page – 1-Nov-2026

## Built
- **List with filters**: scheme, severity, status, "only rules with open issues" (counts `issues` rows with `status = 'OPEN'`, grouped by `rule_id` — the real last-run hit count, not a separate cache). A REFERENCE row (the check stays in code, 2a) shows "Code only" instead of an Edit button.
- **Three-part form** (`forms.tsx`): which rows (hospital / scheme / insurer, valid from/to, which date), what to check (up to 5 conditions, AND/OR, every `ConditionOperator` the engine supports, field/operator/compare-with pickers built from one fixed field list, `packages/rules/src/rule-fields.ts`), what to do (severity E/W only — the retired `'I'` severity and old Tier A–D are not shown, 2a's own "hiding them is 2d's job"). A PARAMETER-type rule (e.g. a TDS rate) gets the simpler name/value form, no condition builder.
- **Save-time conflict check** (`packages/rules/src/conflict.ts`, pure, client-side — no round trip, the rule list is already on the page): same overlapping scope + same field with the opposite operator or a different literal number (CHECK), or the same parameter name with a different value (PARAMETER) — the plan's own example. Shown before Save; a reason is required to save over it, enforced again by `save_rule_version` itself (`P0001` if conflict ids are passed with no reason).
- **Test before save**: `rule_test_runs` (new table) + a worker job (`packages/worker/src/rule-test-runner.ts`) run the single draft against the stored claims of its own scope — read only, never inside the page request (would time out at 130 hospitals). Counts hits per hospital, keeps up to 5 `{tab, row}` examples, no patient data. Save is disabled until the current draft (by content, not just rule id) has a finished test. `packages/rules/src/claim-context.ts` (`contextFromStoredClaim`) rebuilds the engine context from a stored claim's columns, reusing the exact same `evaluateRule`/`ruleInScope` the real engine uses — a test result can never disagree with what a real run would do.
- **Upload (CSV and Excel)**: `packages/rules/src/rule-csv.ts` parses a grid (either format normalised to the same `string[][]` before validation — the `xlsx` package already a web dependency for report downloads); one condition cell holds up to 5 terms (`field OPERATOR value`, joined by `&&`/`||`). Preview shows OK/error per row; "Save N rules" records one `rule_upload_batches` row first (audit) then saves each accepted row tagged with that batch; "Undo this upload" (Owner/Admin only) retires every version from the batch as a group.
- **Plain-words box**: `packages/rules/src/plain-words.ts` builds the prompt and a JSON schema from the same field list the form uses (so the AI can never propose a field the form itself would reject); `apps/web/lib/ai.ts` makes the call (same model/shape as the worker's own AI mapping, `ai-mapping.ts`). No claim or patient data is ever in the prompt. The AI only fills the form; the save action is never given to it.
- **Rights**: `canViewRuleLibrary`/`canEditRuleLibrary` (`lib/roles.ts`) read the `rule_library_view`/`rule_library_add_edit` ticks the database already enforces in RLS — the page's own gate used to ignore ticks entirely (role-only `can(role, "view_rule_library")`), a pre-existing gap now closed as part of "Rights" being explicitly in 2d's scope.
- **`save_rule_version`**: one call, version + conflict note + audit (the existing `rule_versions` audit trigger, `protect_table`, already logs every insert — no separate logging needed). Always inserts PROPOSED; activation stays the separate, already-built `approve_rule_version` (G9) step — editing never skips it.

## Choices made in the build
- Conflict detection runs in TypeScript (`packages/rules`), not SQL: the same "pure code, unit-tested" pattern as `selection.ts`'s own `chooseChecks`/`chooseParameters`, and it means the page shows the conflict with no extra round trip (the rule list is already loaded). `save_rule_version` only re-checks that a reason was given when conflict ids are passed — it does not recompute the conflict itself, the same trust boundary the hospital/dictionary bulk-action patterns already use for their own batch payloads.
- Excel upload was not deferred: `xlsx` (SheetJS) was already a web dependency (claims export), so both formats share one validation path (`parseRuleUploadGrid`) once a file is turned into a plain grid in the browser — no new dependency, no server-side binary parsing.
- A read-time-only flag (row colour unconfirmed, status sources disagree, day-month swap unresolved) is always `false` in a stored-claim test: by the time a claim is stored, its status and dates are already the resolved ones, so a rule that only fires on one of those can never be exercised by this test. Documented in `rule-fields.ts` (`availableInTest`) and `claim-context.ts`, not worked around — those situations genuinely cannot recur against already-cleaned data.
- `rule_test_runs` is a new table rather than reusing `jobs`: `jobs.kind` is `check (kind in ('SHEET_RUN'))` with `sheet_key not null` (a real sheet); a rule test has no sheet and may be scheme- or hospital-wide, so it needed its own narrow table instead of widening `jobs`'s shape for an unrelated kind of work.
